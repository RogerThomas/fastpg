# 0008. TLS

## Context

Hosted PostgreSQL requires TLS, and provider DSNs use libpq's parameters, including
`channel_binding=require`. xitca-postgres 0.4 picks the SASL mechanism itself, accepts
password, md5 or `AuthenticationOk` without SCRAM, and does not report what it used, so it
cannot enforce channel binding.

## Decision

- rustls (ring provider) runs between the socket and xitca, under `EofWatch`.
- DSN keys follow libpq: `sslmode` (`disable`, `prefer` by default, `require`, `verify-ca`,
  `verify-full`), `sslrootcert` (a file or `system`; system roots otherwise), `sslcert` /
  `sslkey`, `sslsni` and `sslnegotiation=direct` (PostgreSQL 17+). Unsupported settings
  such as `sslmode=allow` and `sslpassword` fail with a clear error. Unix sockets never use
  TLS.
- `channel_binding=prefer` (the default) authenticates in xitca; SCRAM over TLS is
  channel-bound when the server offers SCRAM-SHA-256-PLUS.
- For `require` and `disable`, fastpg authenticates itself (`native/src/auth.rs`) with
  postgres-protocol's SCRAM client, then starts xitca over a wrapper that replays the
  server's messages. `require` fails with `InterfaceError`, before any password is sent,
  without TLS, without SCRAM-SHA-256-PLUS, on password or md5, or on `AuthenticationOk`
  before a verified exchange. `disable` uses SCRAM-SHA-256 without binding.

## Consequences

- Common hosted DSNs work unchanged, and dead-connection detection works through TLS.
- `disable` also allows SCRAM over TLS with Ed25519 and Ed448 certificates.
- Nothing is read from `~/.postgresql/` or `PG*` variables, and encrypted client keys and
  CRLs are unsupported.
